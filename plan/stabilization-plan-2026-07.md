## 2. Оставшиеся задачи

### 🔴 Приоритет 1 — регрессия и невыполненные обещания

#### P1-1. Гонка при инициализации синглтона `RAGPipeline`

**Файл**: `core/rag/engine.py:58-64`, `:82-92`

`get_instance()` использует проверку `if cls._instance is None` без блокировки, а
ленивые свойства `collection` / `llm` вызывают `_initialize()` тоже без защиты.

Раньше риск был умозрительным: Gunicorn запускал 3 **процесса**, каждый со своим
инстансом. После перехода на `1 worker + 4 threads` (коммит `e923657`) два
одновременных запроса на холодном старте выполняются в одном процессе и могут
параллельно создать два `chromadb.PersistentClient` на один persist-каталог.
Это ровно тот сценарий повреждения HNSW-индекса, ради устранения которого
воркеры и были схлопнуты в один.

Дополнительно: `cls._instance` присваивается **до** `_initialize()`, поэтому при
падении инициализации в поле остаётся полуготовый объект.

**Решение**: `threading.RLock` на классе, double-checked locking, публикация
инстанса только после успешной инициализации, идемпотентный `_initialize()`.

**Оценка**: XS. **Статус**: сделано (см. раздел 4).

#### P1-2. Нет переиндексации документа

**Файлы**: `core/views/api.py`, `core/views/htmx.py`, `core/urls.py`

`start_indexing_async()` вызывается только из путей загрузки. При этом
CHANGELOG и README обещают: переполненная очередь → документ помечается
`error` → «запустите индексацию повторно». Механизма повторного запуска нет.
Любой `error` (queue full, OOM, недоступная Ollama, таймаут) лечится только
удалением документа и повторной загрузкой файла — файл при этом уже лежит
на диске.

**Решение**:
- `POST /api/docs/<id>/reindex/` → `202` при постановке в очередь, `409` если
  документ уже `processing`, `503` при переполнении очереди;
- HTMX-эндпоинт + кнопка «Переиндексировать» в `partials/doc_list.html`
  для документов в статусе `error`;
- management-команда `reindex_documents [--status=error] [--id=N]`;
- перед постановкой в очередь удалять хвосты предыдущей попытки
  (`delete_document_from_chroma` + `Chunk.objects.filter(document=...)`),
  иначе повторная индексация продублирует чанки;
- сбрасывать `processed_chunks` / `total_chunks` / `error_message`.

**Оценка**: S (полдня). **Статус**: сделано (см. раздел 4).

#### P1-3. Публичные ссылки не отзываются и не истекают

**Файлы**: `core/views/sharing.py:16,40`, `core/models/sharing.py`, `core/urls.py`

`SharedLink.expires_at` объявлен nullable, но `get_or_create()` его не
заполняет — выданный токен действует вечно. Endpoint отзыва отсутствует.
Модель умеет `is_valid`, интерфейс и API — нет.

**Решение**:
- `SHARE_LINK_TTL_DAYS` в `settings.py` + `.env.example` (по умолчанию 30,
  `0` = без срока);
- заполнять `expires_at` при создании ссылки;
- `DELETE /share/<token>/` → `is_active = False` (только владелец);
- список активных ссылок в профиле с кнопкой отзыва;
- тесты: истёкшая ссылка → `410`, отозванная → `410`, чужой отзыв → `403`.

**Оценка**: S (полдня). **Статус**: сделано (см. раздел 4).

### 🟠 Приоритет 2 — устойчивость под нагрузкой

#### P2-1. Длина контекста LLM не ограничена

**Файл**: `core/rag/engine.py:280`

Все прошедшие порог чанки склеиваются без учёта окна модели. При
`SEARCH_K=6 × CHUNK_SIZE=1000` и `OLLAMA_CONTEXT_LENGTH=4096` запас уже
минимальный; повышение `SEARCH_K` через `.env` приведёт к молчаливому
обрезанию промпта на стороне Ollama — пользователь получит ответ по
половине контекста и не узнает об этом.

**Решение**: `MAX_CONTEXT_CHARS` (по умолчанию из `OLLAMA_CONTEXT_LENGTH`
с запасом на инструкцию и вопрос), отбор чанков по убыванию релевантности
до исчерпания бюджета, `logger.info` при отсечении, отражение факта
усечения в `sources`.

**Оценка**: S.

#### P2-2. Нет ограничения частоты на HTMX-эндпоинтах

**Файл**: `rag_project/settings.py:127`, `core/views/htmx.py:42`

DRF throttling покрывает только `/api/`. `/htmx/chat/send/` доступен
залогиненному пользователю без ограничений и занимает единственный
воркер на всё время генерации.

**Решение**: декоратор ограничения на основе Django cache (без новых
зависимостей), `CHAT_RATE_LIMIT` в settings, ответ `429` с понятным
текстом в partial.

**Оценка**: S.

### 🟡 Приоритет 3 — эксплуатация

#### P3-1. Образ Ollama не запинен

`docker-compose.yml:31,59`, `docker-compose.cpu.yml:31,53` используют
`ollama/ollama:latest`. PostgreSQL запинен (`postgres:16-alpine`), Ollama — нет.
Обновление образа на машине заказчика ломает воспроизводимость установки.

**Решение**: `OLLAMA_IMAGE_TAG` в `.env.example`, конкретный тег по умолчанию.
**Оценка**: XS.
**Статус**: сделано 2026-07-29, тег `0.32.5`.

#### P3-2. Нет процедуры резервного копирования

`pg_dump` и снапшоты `chroma_data` не встречаются в репозитории. On-premise
система поставляется без процедуры восстановления.

**Решение**: `scripts/backup.sh` (pg_dump + tar `chroma_data` + `media`),
`scripts/restore.sh`, цели `make backup` / `make restore`, раздел в README.
**Оценка**: S.

#### P3-3. Нет лимита памяти на контейнере django

Ollama ограничена, Django — нет. При исчерпании памяти хоста жертва
выбирается ядром произвольно.

**Решение**: `mem_limit` / `cpus` для сервиса `django` в GPU- и CPU-конфигурациях,
значения через `.env`.
**Оценка**: XS.

#### P4-2. N+1 в списке документов

**Решение**: `.annotate(chunks_total=Count('chunks'))` в `htmx_doc_list`,
`ui.py` и `api_docs_list`.
**Оценка**: XS.

#### P4-3. `file_path` хранится абсолютным
