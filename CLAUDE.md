# CLAUDE.md

## Назначение

Этот файл содержит обязательные инструкции для Claude Code при работе с проектом **ROoP — Rag-Ollama-On-Premises**.

Главная задача проекта — предоставить полностью локальную RAG-систему на базе Django, ChromaDB и Ollama.

Ключевой принцип:

> Все документы, эмбеддинги и запросы пользователей должны обрабатываться внутри локального контура. Не добавляй облачные сервисы и внешние AI API без прямого указания пользователя.

---

## Кратко о проекте

ROoP — локальная система Retrieval-Augmented Generation со следующими возможностями:

* загрузка и индексация документов;
* извлечение текста из PDF, TXT и Markdown;
* разбиение текста на чанки;
* генерация эмбеддингов;
* хранение векторов в ChromaDB;
* семантический поиск по документам;
* генерация ответов через Ollama;
* поддержка Ollama через Open WebUI;
* Django UI с HTMX;
* REST API;
* регистрация и аутентификация пользователей;
* изоляция документов и чатов между пользователями;
* предоставление общего доступа к документам и чатам;
* отображение прогресса индексации;
* восстановление документов после прерванной индексации.

## Основные архитектурные правила

### Разделение ответственности

Соблюдай существующее разделение модулей.

#### `core/models/`

Содержит модели данных и ограниченную доменную логику:

* пользователи;
* документы;
* чаты;
* общий доступ.

Не размещай здесь:

* HTTP-логику;
* вызовы Ollama;
* работу с ChromaDB;
* обработку шаблонов;
* длинные сценарии индексации.

#### `core/views/`

Представления разделены по назначению:

* `api.py` — REST API;
* `ui.py` — обычные HTML-страницы;
* `htmx.py` — HTMX-запросы и partial responses;
* `sharing.py` — публичный или ограниченный общий доступ;
* `helpers.py` — общие функции представлений.

Не превращай один модуль в универсальный файл со всей логикой приложения.

Представления должны:

1. проверить аутентификацию и права;
2. провалидировать входные данные;
3. вызвать соответствующую прикладную или RAG-логику;
4. вернуть ответ.

#### `core/rag/`

Содержит RAG-компоненты:

* `extractor.py` — извлечение текста;
* `chunker.py` — разбиение текста;
* `backends.py` — взаимодействие с LLM и embedding backend;
* `store.py` — работа с векторным хранилищем;
* `engine.py` — координация поиска и генерации ответа.

Новая логика конкретного компонента должна добавляться в соответствующий модуль.

Не размещай всю новую RAG-логику в `rag_pipeline.py`. Перед изменением `rag_pipeline.py` проверь, не является ли он фасадом или слоем обратной совместимости.

#### `core/indexing.py`

Используется для координации индексации документов, прогресса и обработки ошибок.

Изменения индексации должны учитывать:

* переходы статусов;
* прогресс обработки;
* повторный запуск;
* частично записанные данные;
* очистку после ошибки;
* таймауты;
* нехватку памяти;
* перезапуск приложения.

## Обязательные инварианты

Не нарушай следующие условия.

### Полностью локальная работа

По умолчанию запрещено добавлять:

* OpenAI API;
* Anthropic API;
* Google Gemini API;
* облачные embedding API;
* облачные векторные базы;
* внешнюю аналитику;
* внешнюю телеметрию;
* отправку документов во внешние сервисы.

Open WebUI допустим только как настроенный пользователем локальный или внутренний прокси.

### Изоляция пользователей

Документы, чаты, сообщения и векторные данные одного пользователя не должны быть доступны другому пользователю без явно оформленного общего доступа.

Проверка доступа должна выполняться не только в интерфейсе, но и на серверной стороне:

* в queryset;
* при получении объекта;
* перед удалением;
* перед скачиванием;
* перед поиском в ChromaDB;
* перед генерацией ответа;
* в REST API;
* в HTMX endpoints;
* в shared views.

Нельзя полагаться на скрытую кнопку или отсутствие ссылки в интерфейсе.

### Общий доступ

При работе с публичными ссылками и объектами общего доступа необходимо учитывать:

* срок действия;
* статус ссылки;
* владельца;
* разрешённый тип доступа;
* невозможность перебора идентификаторов;
* отзыв доступа;
* отсутствие утечки внутренних путей и служебных данных.

Не логируй токены общего доступа целиком.

### Согласованность PostgreSQL и ChromaDB

Операции с реляционными данными и векторами должны оставлять систему в предсказуемом состоянии.

При ошибке индексации:

* документ должен получить корректный статус;
* пользователю должна возвращаться понятная ошибка;
* частично созданные векторы не должны использоваться как завершённый индекс;
* повторная индексация не должна бесконтрольно дублировать чанки;
* временные ресурсы должны очищаться, когда это безопасно.

### Секреты

Запрещено:

* добавлять `.env` в Git;
* записывать реальные пароли в код;
* использовать production-секреты в тестах;
* выводить API-ключи и пароли в логи;
* помещать секреты в URL;
* возвращать секреты в API-ответах.

Все секреты должны поступать из переменных окружения.

## Порядок выполнения задач

Для любой задачи придерживайся следующего порядка.

### 1. Изучи контекст

Перед изменением кода:

* найди связанные файлы;
* изучи вызывающий код;
* изучи модели и ограничения;
* найди существующие тесты;
* проверь миграции;
* проверь настройки;
* проверь существующие интерфейсы и контракты.

Не начинай реализацию только по названию файла или функции.

### 2. Сформулируй минимальное изменение

Предпочитай небольшой целевой патч.

Не выполняй одновременно:

* переименование несвязанных модулей;
* массовое форматирование;
* архитектурный рефакторинг;
* обновление всех зависимостей;
* изменение публичного API,

если это не требуется задачей.

### 3. Сначала исправь причину

Не маскируй проблему:

* дополнительными `try/except`;
* отключением проверки;
* увеличением таймаута без анализа;
* игнорированием исключения;
* возвратом пустого результата;
* удалением падающего теста.

Определи первопричину и добавь регрессионный тест.

### 4. Добавь или обнови тесты

Любое изменение поведения должно сопровождаться тестом.

### 5. Запусти проверки

Сначала запускай узкие тесты, затем полную проверку.

Пример:

```bash
poetry run pytest core/tests/test_rag_search.py -q
make check
```

### 6. Обнови документацию

Обновляй документацию при изменении:

* переменных окружения;
* команд;
* API;
* форматов запросов;
* статусов;
* процесса индексации;
* Docker-конфигурации;
* поддерживаемых файлов;
* требований к системе.

Новая переменная окружения должна быть добавлена как минимум в:

* код настроек;
* `.env.example`;
* документацию;
* тесты настроек, когда они существуют.

### 7. Подготовь итог

В итоговом сообщении укажи:

* что изменено;
* почему;
* какие файлы затронуты;
* какие тесты запущены;
* результат проверок;
* оставшиеся риски или ограничения.

Не утверждай, что тесты прошли, если они не запускались.

## Python-стиль

Следуй конфигурации Ruff из `pyproject.toml`.

Основные правила:

* используй понятные имена;
* добавляй type hints к новой прикладной логике;
* не используй изменяемые значения как аргументы по умолчанию;
* не применяй голый `except`;
* перехватывай конкретные исключения;
* не подавляй исключения без логирования или осознанной обработки;
* используй `logging`, а не `print`;
* используй timezone-aware даты;
* предпочитай `pathlib.Path` для файловых путей;
* избегай скрытых глобальных изменяемых состояний;
* не создавай singleton без необходимости;
* не дублируй существующую логику;
* сохраняй функции небольшими и тестируемыми;
* комментарии должны объяснять причину, а не повторять код.

Не добавляй `# noqa`, `type: ignore` и аналогичные исключения без конкретного обоснования.

## Правила Django

### Модели

При изменении модели:

1. измени модель;
2. создай миграцию;
3. изучи сгенерированную миграцию;
4. проверь обратную совместимость;
5. обнови фабрики и фикстуры;
6. обнови тесты;
7. запусти миграции на чистой тестовой базе.

Не редактируй старые применённые миграции ради исправления текущей схемы. Создавай новую миграцию, если пользователь не указал обратное.

Для потенциально опасных изменений данных используй отдельную data migration.

### Транзакции

Используй `transaction.atomic()` там, где несколько изменений PostgreSQL должны применяться совместно.

Не удерживай транзакцию базы данных во время длительных операций:

* HTTP-запросов к Ollama;
* генерации эмбеддингов;
* обработки большого файла;
* записи большого количества векторов;
* ожидания внешнего процесса.

### QuerySet

Избегай N+1 запросов.

При необходимости используй:

* `select_related`;
* `prefetch_related`;
* `only`;
* `values`;
* агрегацию на стороне базы.

Не оптимизируй запросы вслепую: сначала установи проблему тестом, профилированием или анализом SQL.

### Формы и сериализаторы

Валидация входных данных должна находиться на сервере.

Не доверяй:

* расширению файла;
* MIME-типу от клиента;
* имени файла;
* переданному идентификатору владельца;
* размеру, заявленному клиентом.

### Настройки

Не добавляй окружение-зависимые значения непосредственно в `settings.py`.

Используй переменные окружения и безопасные значения по умолчанию только для локальной разработки.

Не ослабляй без прямого требования:

* `DEBUG`;
* `ALLOWED_HOSTS`;
* CSRF-защиту;
* cookie security;
* проверку API-ключа;
* ограничения загрузки файлов.

## Правила RAG-пайплайна

### Извлечение текста

При изменении `extractor.py`:

* проверяй пустые документы;
* обрабатывай повреждённые файлы;
* ограничивай ресурсоёмкие операции;
* не возвращай пользователю внутренние пути;
* не считай расширение файла достаточным доказательством формата;
* добавляй тесты для поддерживаемых форматов.

### Разбиение на чанки

Изменение `CHUNK_SIZE` и `CHUNK_OVERLAP` влияет на:

* качество поиска;
* размер ChromaDB;
* скорость индексации;
* количество запросов на embeddings;
* расход памяти;
* контекст LLM.

При изменении алгоритма чанкинга проверь:

* отсутствие пустых чанков;
* стабильный порядок;
* корректное перекрытие;
* обработку короткого текста;
* обработку очень длинного текста;
* сохранение связи с документом;
* воспроизводимость результата.

### Embeddings

При работе с embeddings:

* используй пакетную обработку;
* учитывай `EMBED_BATCH_SIZE`;
* не загружай весь большой корпус в память без необходимости;
* обрабатывай таймауты;
* проверяй размерность векторов;
* учитывай смену embedding-модели;
* не смешивай в одной коллекции несовместимые embeddings без стратегии миграции.

Смена `EMBED_MODEL` может потребовать полной переиндексации документов. Это должно быть явно отражено в документации.

### Векторное хранилище

При записи в ChromaDB сохраняй метаданные, необходимые для:

* определения документа;
* определения владельца;
* фильтрации доступа;
* удаления всех чанков документа;
* отображения источников;
* диагностики индексации.

Поиск должен ограничиваться документами, доступными текущему пользователю.

Нельзя сначала получить глобальные результаты из ChromaDB, а затем скрыть запрещённые документы только на уровне шаблона.

### Поиск

Учитывай настройки:

* `SEARCH_K`;
* `SEARCH_RELEVANCE_THRESHOLD`.

Не меняй смысл relevance score без обновления тестов и документации.

Проверь граничные случаи:

* ничего не найдено;
* найден только нерелевантный контекст;
* пользователь не имеет документов;
* документ ещё индексируется;
* документ завершился ошибкой;
* доступ есть только через shared link;
* ChromaDB временно недоступна.

### Генерация ответа

LLM должна получать только разрешённый контекст.

Не включай в prompt:

* чужие документы;
* реальные секреты;
* внутренние пути;
* API-ключи;
* stack trace;
* лишние системные метаданные.

Ответ без релевантного контекста не должен притворяться ответом из документов. Система должна явно сообщать, что подходящая информация не найдена.

### Backend Ollama и Open WebUI

Сохраняй единый внутренний интерфейс backend.

Различия между Ollama и Open WebUI должны быть изолированы в `core/rag/backends.py` или соответствующем слое.

Не размазывай проверки вида:

```python
if backend == "ollama":
    ...
elif backend == "openwebui":
    ...
```

по всему приложению.

При добавлении нового backend необходимы:

* единый контракт;
* конфигурация;
* обработка ошибок;
* таймаут;
* тесты;
* документация;
* безопасная работа с ключами.

## API

REST API должен сохранять обратную совместимость, если задача явно не требует breaking change.

Для изменения endpoint проверь:

* URL;
* HTTP-метод;
* аутентификацию;
* права доступа;
* request schema;
* response schema;
* коды ответа;
* обработку ошибок;
* тесты;
* примеры в README.

API-ключ передаётся через заголовок:

```http
Authorization: Api-Key <key>
```

Не добавляй передачу API-ключа через query string.

Используй корректные статусы HTTP:

* `200` — успешное получение или действие;
* `201` — создание;
* `202` — принятая асинхронная операция;
* `204` — успешное удаление без тела;
* `400` — неверные данные;
* `401` — отсутствует или неверна аутентификация;
* `403` — недостаточно прав;
* `404` — объект отсутствует или недоступен;
* `409` — конфликт состояния;
* `413` — слишком большой файл;
* `429` — превышение лимита;
* `500` — непредвиденная серверная ошибка;
* `502`/`503`/`504` — проблемы с зависимым локальным сервисом.

Не возвращай пользователю необработанный stack trace.
